Part I. Project Background and Problem Statement

  1. Project Title Chainy: A 3D World Educational Game for Learning Emerging

Technology (Blockchain & AI)

  1. Problem Statement

Young learners have limited access to age-appropriate, safe, and engaging educational materials about emerging technologies such as blockchain and artificial intelligence (AI). Most existing learning resources rely on complex technical jargon or adult-oriented financial speculation. Additionally, unstable internet connectivity in underserved communities prevents continuous access to online educational platforms.

  1. Target Users

Primary school children aged 6–12 years old (Kindergarten to Elementary / Grades 1 to 6) from Cryptita Plays outreach programs and community mini-library beneficiary sites.

  1. Purpose of the Proposed System To introduce foundational concepts of blockchain and artificial intelligence through an interactive 3D exploration and puzzle game. Learners explore a top-down 3D world with technology-building mechanics, accompanied by 2D/UI-driven mini-games for validation and classification. The system is built with a strictly offline-first architecture to run reliably on affordable mobile devices.

  2. Reason Why the Problem Is Worth Solving

Emerging technologies are transforming modern computing, yet young learners lack structured, age-appropriate foundations. By translating abstract concepts into gamified simulations, children develop early computational thinking and digital safety awareness without financial risk. Ensuring complete offline access on low-to-mid-range Android devices democratizes STEM education for underserved learners who lack consistent internet connectivity.

Guide Questions

  1. What problem does your proposed system aim to address? Chainy addresses the scarcity of age-appropriate, interactive educational resources that teach foundational blockchain and artificial intelligence concepts to young learners. Current introductory materials are overly technical and text-heavy, while dependency on continuous broadband internet access excludes students in resource-constrained communities from participating in digital education.
  2. Who experiences this problem? The primary beneficiaries are children aged 6–12 years old within elementary schools, community mini-libraries, and Cryptita Plays educational outreach programs. Elementary educators and parents also experience this problem due to a lack of safe, non-speculative instructional tools for emerging technologies.
  3. Why is this problem important? Foundational digital literacy must evolve alongside technological innovation. If young students are not introduced to the operational logic of distributed networks, data verification, and machine learning principles early on, the digital knowledge divide will widen, leaving them ill-prepared for future STEM and computational environments.
  4. What is the main purpose of your proposed system? The main purpose of Chainy is to deliver an engaging, 3D game-based learning platform where young learners actively explore concepts through technology-building mechanics, transaction validation, tamper detection, pattern classification, and checkpoint quizzes.
  5. Why should this project be considered for further development? Chainy presents a well-defined pedagogical scope, a clear target demographic, and an offline-first technical pipeline optimized for accessible mobile hardware. It bridges academic computer science principles with community outreach needs, providing a scalable prototype for early childhood technology literacy.

Multi-touch screen gestures: virtual joystick controls for 3D exploration, tap-to-interact triggers for objects/NPCs, drag-and-drop actions for sorting puzzles, and UI buttons for quiz answers.

How do these components work together to make your proposed system function? Chainy operates as an integrated system where user touch inputs are captured by the Android OS and interpreted by Unity C# logic scripts to manipulate 3D game objects, UI states, and puzzle mechanics. The operating system allocates RAM and schedules CPU/GPU cycles to render low-poly 3D environments and process real-time game logic. In-game accomplishments dynamically trigger visual and auditory feedback, while player progress is automatically serialized to local JSON files. Because the system is architected as an offline-first application, all game assets and databases are self-contained on the device storage, ensuring a continuous learning loop that functions independently of external network infrastructure.

Guide Questions

  1. Why are these hardware requirements appropriate for your proposed system? They balance the visual and computational demands of a 3D game engine with the practical hardware profiles of budget Android devices found in community learning environments.

  2. Why was this operating system chosen? Android was selected because Chainy is designed primarily for smartphones and tablets that are accessible to the target users. Android also provides the robust operating system services needed for application execution, memory management, file storage, touchscreen input, audio, security, and graphics processing (Ekanayake, 2018).
  3. What operating system services will your proposed system use? Chainy will use process management, memory management, file management, device management, CPU scheduling, networking, and security and permissions to manage the game’s execution, resources, local files, hardware, and system access.

Part V. Memory and Application Performance Planning

  1. What parts of the system may consume memory? The primary memory overhead in Chainy stems from the top-down 3D scene elements, particularly the character meshes, node/block prefabs, texture atlas sheets, and visual UI overlays. Secondary memory allocations include uncompressed audio streams for background music and interactive sound effects, active particle emitters for reward feedback, and runtime data structures used to track puzzle validation states
  2. What resources will be loaded while the system is running? During an active session, the game engine loads the current level's 3D terrain geometry, player controller scripts, interactive building blocks, and sorting puzzle assets into volatile memory. It also holds the active HUD interface, audio playback clips, assessment quiz question structures, and the player's real-time progress buffer before it gets written to local storage
  3. What could cause performance problems? Performance degradation can be triggered by rendering too many unbatched 3D objects at once, using high-resolution uncompressed textures, or running complex calculations inside per-frame update loops. Additionally, failing to clear previous scene assets during level transitions and forcing the mobile GPU to calculate dynamic real-time shadows will quickly overburden low-to-mid-range hardware.

  1. What performance problems might users experience? Learners may encounter noticeable frame rate drops (stuttering below 30 FPS), delayed touch inputs when moving the character, extended scene loading times, device overheating, or sudden application crashes if the device runs out of available RAM.

Part VI. Networking Requirement Analysis If your proposed system is offline, answer the following:

  1. Why does your system not require internet access? The entire core instructional pipeline of Chainy including the 3D top-down exploration worlds, technology-building mechanics, validation mini-games, and assessment quizzes is packaged directly within the local installation. Since the target learners in community mini-libraries and outreach centers may lack reliable or affordable Wi-Fi, the game is built to operate independently on local hardware to prevent connectivity-based interruptions.
  2. What data or files will be stored locally? Game assets, educational content, settings, scores, completed activities, and player progress stored through JSON files will be kept locally.
  3. What features could be added in the future that may require networking? Future features may include student analytics, downloadable educational content and updates, and integration with educational materials Offline Requirement

Explanation

Reason for Offline Use

Chainy is intended to remain accessible even when the user does not have a stable internet connection. The main 3D exploration, lessons, puzzles, mini-games, and progress tracking do not require constant online communication.

Locally Stored Data

User settings, learning progress, completed activities, scores, game state, and other save information will be stored locally using JSON.

The device must have enough storage for the application, 3D models, textures, audio, animations, UI assets, educational materials, mini-games, and locally stored progress.

Future versions could include game/content updates, optional student analytics, additional downloadable educational materials, or integration with partner organizations.

Part VIII. Technical Feasibility Conclusion At this preliminary milestone, Chainy is technically viable for development, provided that development parameters remain tightly scoped and tailored to the hardware profile of our target audience. The primary technical strength of this system lies in its standalone, offline-first design. By packaging the 3D learning modules, interactive puzzle mechanics, and progress tracking directly on the device, the game operates independently of remote database servers and high-speed internet, making it well-suited for deployments in partner community mini-libraries. Selecting Android further enhances accessibility by allowing the application to reach students across a wide range of affordable mobile hardware. The most significant technical challenge involves managing runtime 3D rendering and memory footprint on entry-level mobile chipsets. Unoptimized low-poly geometry, uncompressed textures, real-time lighting calculations, or unpooled object instantiation can quickly exhaust volatile memory and overburden mobile graphics processors. While modern mid-range devices handle these tasks easily, our primary beneficiaries frequently rely on older or budget Android smartphones and tablets. Without proactive asset optimization, the application risks thermal throttling, frame rate drops below 30 frames per second, delayed touch inputs, or unexpected memory-related terminations. To mitigate these risks before entering full production, our development workflow will establish strict asset budgets for 3D polygon counts, rely exclusively on pre-baked lightmaps, and compress user interface and texture atlases to mobile standards. Furthermore, we will build a vertical-slice prototype and conduct performance profiling using the Unity Profiler directly on physical budget Android test units. Based on this technical evaluation, the project should continue into active development. The team will prioritize constructing a streamlined Minimum Viable Product focusing strictly on the three foundational learning tracks blockchain validation, tamper detection, and artificial intelligence data classification while deferring secondary cloud-based features and educator analytics to subsequent development milestones.
