SQLite database schema — Chainy​

Capstone project title: Chainy: A 3D World Educational Game for learning emerging Technology (Blockchain & AI)

Approved scope supersession — October 8, 2026: The user selected essential fundamentals for ages 12–17, especially underserved/remote learners with limited technology access, through tappable Web3, Blockchain and AI worlds. Full A–Z coverage is withdrawn. Free spatial construction and mandatory walkable 3D/joystick navigation are deferred; use bounded order/link activities, guided three-local-replica comparison, a genuine tiny classifier validated before production, and a short fixed-grid agent. The nine lesson IDs W1–W3, B1–B3 and A1–A3 are a draft curriculum, not a confirmed count. Current baseline/GDD/curriculum take precedence over historical issue titles and old level IDs below. Phone specifications, SQLite/export, rubric and November 21 deadline remain. The old 520-hour estimate has not been recosted for this scope.

Version 0.1 • October 8, 2026 • Proposed local storage design. The user clarified that “background schema” means SQLite database schema. local-schema.sql is executable proposed v1 DDL, not evidence of a shipped database or migration. SQLite is the authoritative local store; JSON is only a checkpoint encoding/export format. See technical requirements, app flow and offline evidence plan.

Entity relationships​

schema_meta is a separate singleton table with positive integer version; it tracks local schema migration independently of app and content versions. Composite keys in the diagram must be interpreted together, not as independently unique columns.

Data dictionary and ownership​

export_batches(export_id)Random globally unique ID; contextual creation time; positive schema version; nonnegative attempt count; optional digest/receipt; statusprepared, written, received, failed; transfer status is not progress

Attempt event_kind is one of puzzle_result, quiz_answer, pretest_answer, posttest_answer. An event identifies one scored/unscored response or meaningful puzzle result. Proposed quiz convention: activity_id identifies a stable question/result definition, so no free-text question or response is required. The versioned content catalog resolves its level, question and objective. Use fixed answer_code values such as answer option IDs or enumerated puzzle outcome codes; never arbitrary learner text. Research pre/post events require an approved nonempty instrument_version; formative puzzle/quiz events may leave it null. Do not collect extra research metrics simply because storage permits them.

Generate random installation/session/event/export IDs independently of wall-clock time. Installation identity is held in app-private configuration and may change after reinstall. It is not a learner identity. On reinstall, learner code re-entry cannot restore deleted local progress.

SQL guarantees versus application guarantees​

The DDL enforces primary keys, parent relationships when foreign keys are enabled, unique session sequences, enumerated statuses/kinds, Boolean values and nonnegative counters. No cascade deletion is defined: deleting a referenced parent fails. The redundant-looking session lookup index is harmless; performance tuning should follow the actual binding/workload.

The application must enforce all of the following; the DDL alone does not:

  • Enable and verify PRAGMA foreign_keys=ON on every connection before transactions. Use bound parameters and reject blank/oversized identifiers and malformed timestamps.
  • Normalize proposed teacher codes consistently (trim and uppercase only for the adopted unambiguous alphabet); preserve a documented study namespace. Reject unsupported characters instead of silently converting a code into another learner's code.
  • Treat attempts as immutable: expose insert/read through the persistence interface; do not offer ordinary update/delete. SQLite contains no append-only trigger here, so direct privileged SQL could still edit them.
  • Generate sequence_no under the single writer transaction as the next per-session number; elapsed durations come from a monotonic timer, not timestamp subtraction. Validate finite bounded payload numbers.
  • Require end time for completed/interrupted sessions, no end time for active sessions, and a valid state transition; do not interpret unreliable device clocks as accurate elapsed time.
  • Validate event kinds against content and instrument catalogs. Correctness is null for unscored events, otherwise 0 or 1; recording an answer does not alone complete a level.
  • Apply payload byte/element limits and version checks; reject graph references to missing components, incompatible activities and out-of-bounds placements. Do not rely on SQLite JSON extensions.
  • Treat record_count as number of included attempt rows, not total rows across all arrays; it must equal export_events membership and the manifest's event count.
  • Require a verified file/digest before written; require a matching receipt and reviewed counts before received. A digest detects accidental change, not identity or authenticity.

Checkpoint payload contract​

Proposed JSON encoding lives in progress.checkpoint_payload; this does not replace SQLite persistence. An envelope contains payload_version, activity_id, activity_version, phase and state. state contains only the data needed to resume the current activity: bounded record order and predecessor selections, guided replica exercise state, learner-selected examples/policy where relevant, quiz cursor and references to completed submissions. Exclude Unity object references, arbitrary executable code, unrestricted free text and transient animation/frame state.

Use content-defined completion to derive level unlocks and badges from progress.completed. This v1 schema has no independent badges or settings table. If adjustable audio/text preferences ship, store non-research device-wide settings in app-private configuration; add a reviewed schema migration only if per-profile settings or independent badge awards become necessary. Do not promise invisible columns already exist.

The primary key keeps one current checkpoint per profile and level, across content versions. Before replacing a checkpoint for new content, either migrate its versioned payload under a tested rule or explicitly start the activity at a safe point with explanation. Preserve immutable attempts; do not re-score old events under new rules. Session content version continues to identify historical evidence.

Write transactions and interruption​

Create/select profile: after new-profile confirmation, insert the learner if absent; selecting an existing key does not overwrite it. Start mission: create the session with app/content versions before accepting evidence.

Submit outcome: allocate event ID once outside retry, then begin a short write transaction. If it exists, compare the stored immutable fields; identical means already committed, different means conflict. Otherwise allocate sequence, insert attempt and update checkpoint/completion together. Commit before returning success or showing a badge. On rollback retain the same pending submission ID. An identical already-committed event must not reapply an older checkpoint over newer progress.

Leave/relaunch: close a deliberately ended unfinished session as interrupted; after process restart, mark stale active sessions interrupted and create a new one on resume. A terminated process loses only uncommitted edits, never previously committed results. Session completion and level completion have different meanings and must not be conflated.

Busy/locked, storage-full and failed commit return explicit failures. Keep write transactions short and serialized. A recovery screen must preserve existing data and must not silently create a new empty database over a corrupt/unsupported one.

Export snapshot and lifecycle​

  1. Select an approved scope. In a short consistent transaction capture selected immutable events and their parent sessions/learners, plus exact schema/app/content/instrument versions; insert prepared batch and event memberships. Freeze the captured serializable snapshot in memory or an app-private temporary file so mutable session end/status fields cannot drift while writing. Do not hold a transaction open while the user operates the picker.
  2. Build a versioned envelope: format_version, export_id, schema_version, created_at, event_count, version sets, minimal learner/session arrays, attempts array and digest. Export no progress checkpoint by default because research export is not save transfer.
  3. Recommended digest contract: hash the exact UTF-8 bytes of a defined payload section with SHA-256, storing algorithm/encoding alongside the digest. Exclude the digest itself from the hashed bytes; importer validates the original bytes. Freeze the actual wire format with synthetic fixtures in CH-11 rather than depending on incidental JSON property order.
  4. Write through the verified Android picker adapter, then record digest and written only after confirmed write completion. Cancellation/failure records failed without deleting events. An incomplete destination file is never a valid receipt; explain its removal/retry to staff.
  5. Retry the same frozen snapshot/export ID if it remains available. If it cannot be reproduced byte-for-byte, prepare a new export ID; stable event IDs still prevent duplicate research totals.
  6. A validated importer receipt identifies export/digest and accepted, duplicate and rejected counts. Mark received only after staff verifies the expected events are accepted or already present without unresolved conflicts. Otherwise retain actionable written/failed status and counts in the importer report. No export status authorizes deletion on its own.

The v1 local table stores only a receipt reference, not detailed importer statistics. Store the full receipt/report in the approved staff destination; add columns only if an agreed UI needs structured local counts. A successful local save and teacher receipt are separate facts.

Import, duplicates and conflicts​

The external importer uses its own reviewed aggregate schema; this device schema is not an automatic cloud database. Validate file size, format/schema versions, counts, digest, required parent references and fixed content/instrument identifiers before applying data. Treat unknown/incompatible content as rejected or quarantined, never silently remapped.

Deduplicate attempts globally by event_id. Same ID and identical immutable event data → duplicate; same ID with different data → quarantine conflict and never overwrite accepted evidence. Also validate session identity/version fields and sequence uniqueness; the same session ID with incompatible ownership or content versions is a conflict. Session end/status is a mutable envelope: allow only documented compatible lifecycle advancement, and quarantine contradictions rather than dropping new valid attempts as if already imported. Earlier incomplete-session snapshots must not erase a later completed/interrupted state.

Use an aggregate transaction for each validated package and keep a durable package/receipt record. Whole-package rejection is the recommended first implementation for malformed/conflicting packages; report zero newly accepted records and explicit reasons. Re-import after a successful package must not change research totals. Combining learner sessions across installations is research linkage, not device save restoration.

Migration, backup, retention and recovery​

Pin schema version separately from app, content and instrument versions. A schema newer than the binary supports blocks writes and asks for a compatible signed app. Do not use CREATE TABLE IF NOT EXISTS as a substitute for a versioned migration.

Before changing an existing database, create a consistent backup using the selected binding's supported method or a verified closed-database procedure that accounts for journal files. Never copy only a live main SQLite file while writes/WAL may be pending. Apply ordered migrations in a transaction where supported, validate row counts, foreign keys and integrity, update schema_meta only on success, and preserve the previous recoverable copy if any step fails. A content-only change still needs checkpoint compatibility review even when schema version stays 1.

Ordinary SQLite is not encrypted storage. Device custody, Android backup behavior, permitted transfer destination and protection must be explicitly reviewed. The research lead must supply retention/deletion rules; deleting data after a receipt is not automatic. Parent-first deletion fails by design, so an authorized purge implementation must delete dependent memberships/events/sessions/progress in a tested transaction and remove orphan batch metadata as policy requires. Synthetic test records are the only fixtures allowed in repositories/issues.

Verification and ownership​

Host-side DDL validation checks table creation, foreign-key enforcement, duplicate IDs/sequences, invalid values, two-profile keys, export membership and rollback. This proves SQL behavior on the host only; Android adapter/ABI, actual process lifecycle, backups, picker behavior, signed updates and device performance still require CH-04/14 evidence.

Shared DTO/export changes require coordinated review before independent agent work merges. CH-04 gates persistence consumers and CH-11 gates collection readiness. Lesson identifiers after the approved three-world revision​

The v1 SQL column progress.level_id remains a text content key; it is not restricted to integers or three entries. For new content it identifies one lesson (draft W1–W3, B1–B3, A1–A3), while the versioned content catalog maps each lesson to Web3, Blockchain or AI and defines its activities/prerequisites. Nine is a draft count. World completion is derived from the agreed versioned lesson set; do not hard-code three old levels or nine final lessons in SQL/UI.

The earlier L1/L2/L3 activity catalog and newer lesson IDs are different content versions. Define an explicit reviewed mapping before importing/migrating old checkpoints. Never rename historical attempt IDs, fabricate completion for a new lesson from an old level, or delete evidence to fit the new structure. Unsupported old checkpoint payloads restart at an explained safe lesson point while immutable attempts retain their original IDs/versions. No schema-column rename or destructive migration is authorized by this document update; test the actual content migration in CH-04. Export/import must carry and resolve both catalogs where historical records exist.
