Chainy local database reference​

Owner: Christian Jude Villaber. Updated October 12, 2026 from the supplied technical design.

SQLite stores data on the device. The user requested documentation adoption, not changes to the running game's database. The previous generated learners/sessions/attempts/export-table schema has been archived. It must not be applied as the current design.

V2 persistence requirements — October 23, 2026​

The canonical GDD adds requirements not represented by the five-entity source dictionary below. Persist profile ID; build/content/schema versions; quest state and reward receipts; encyclopedia progress; inventory and balances; the shared lantern transaction/ledger; restoration flags; and activity checkpoints. AI training/practice/first-final-test state is needed only if the stretch is admitted.

Treat these as required record semantics, not approved SQL table names. Christian must inspect the actual schema, design the smallest compatible extension and test recovery before any migration. A purchase/reward must atomically update balance, ownership, ledger and quest progress; command/save retries must not repeat the economic effect. W03 expects reward 12, price 8 plus fee 1 and remaining balance 3. W04 equip is free.

The November 10 beta uses local demo profiles. Full teacher activation, protected roles and offline pairing are later service contracts; the old isTeacher flag does not implement them.

Decisions before schema changes​

Christian resolves these on CH-04, with Sean reviewing evaluation needs:

  1. Export the actual table definitions and confirm full names, types, keys and schema version.
  2. Choose one learner-code format. Recommendation: TEXT if codes allow letters or meaningful leading zeroes. Do not silently convert existing records.
  3. Define one score rule and one meaning for attempts; state the percentage denominator and rounding. A maximum score is mentioned in validation but not defined in the dictionary.
  4. Enforce one current progress row per user/lesson if that is the intended model. Decide whether earlier attempts must be retained separately for the approved study.
  5. Define User_Analytics. Recommendation: derive reports from authoritative records where possible instead of copying mutable scores into a second table. A historical snapshot needs an explicit identifier and meaning.
  6. Identify the fields that support the promised session/checkpoint behavior. Decide a safe resume point; avoid saving transient animation state.
  7. Confirm whether username/age are necessary. Keep identity maps and raw learner data outside repositories and issues.

These recommendations do not override the Tech Lead's schema. The supplied dictionary is not detailed enough to safely manufacture SQL or a migration.

Required validation and save behavior​

The source requires unique non-null keys, valid parent relationships, nonblank required text, valid ages/Booleans, ordered lessons, unique current progress and bounded scores. Christian must implement these in the actual schema/application.

SQLite does not enforce the length in VARCHAR(30), and Boolean values use integer storage. Explicit validation is needed. See SQLite types.

Enable and verify foreign-key enforcement on each database connection. See SQLite foreign keys.

Use bound query parameters. Save related score/completion changes together, and return success only after commit; failed writes must preserve the previous save. See SQLite transactions.

A repeated completion/save request must not inflate attempts or award progress twice. Christian chooses the smallest repeat-safe approach consistent with the actual schema. Do not retrofit the old event/export framework without a demonstrated need.

Lifecycle and collection​

Create/select profiles locally; isolate them on shared devices. A code entered on another phone does not restore records. Keep a supported checkpoint for resume, with clear feedback after interruption.

Before any real database change, record the existing version, back up consistently, test the change using synthetic data and verify that an in-place app update preserves records. This document authorizes no deletion or migration.

Teacher collection is a separate workflow in the offline data plan. SQLite storage does not upload records automatically. Research exports should contain only approved fields and enough identifiers to avoid counting the same result twice.

Acceptance evidence​

CH-04 needs: actual schema + two-profile isolation + result save/reload + retry without duplicate counting + failed-save recovery. CH-14 adds interrupted play and in-place update checks on the beta device. Record build, device, expected result, actual result and reviewer.
