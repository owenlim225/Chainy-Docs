Chainy game design​

Current gameplay direction, October 12, 2026. Based on Christian Jude Villaber's technical design and the user's explicit replacement of the earlier plan.

Purpose and audience​

Chainy introduces foundational Web3, Blockchain and AI concepts through an offline 3D Android game for ages 12–17. Use plain English, visual examples and short explanations. Assume that some players are new to touch controls and the subject matter.

The game is single-player. Learning about blockchain and AI does not require real cryptocurrency, an online blockchain, or a cloud AI service.

Player experience​

  1. Open the game and create or select a local learner profile.
  2. Enter a learning level and move through the 3D scene.
  3. Interact with the lesson or dialogue to learn a concept.
  4. Start one Quiz, Wordle or BlockMatch activity.
  5. Read the result and explanation. Retry according to that activity's rules.
  6. Save progress, then continue or leave. Returning players load this device's saved progress.

The actual level layout, movement controls and lesson sequence must be agreed by Sherwin and Christian. The previous tappable nine-lesson map is no longer the gameplay specification.

The three mini-games​

ModeEstablished by the technical designRules still to freeze on CH-02Completion check
QuizShows questions, evaluates answers and calculates scores; current UI reads ScriptableObjectsApproved question set, scoring, pass/completion rule, retry handlingCorrect and incorrect answers produce the expected score and explanation; saved result reloads
WordleValidates guesses and evaluates lettersEducational word list and definitions, word length, guess limit, repeated-letter feedback, win/loss/retry ruleValid/invalid guesses, repeated letters, win and exhausted attempts behave as agreed
BlockMatchBoard operations, matches, cascades and objectives; uses pooled objectsWhat counts as a match, learner meaning, board limits, move/time rule, no-move case, cascade/end ruleLegal/illegal moves, cascade completion, win/loss and no-move handling match the agreed rules

A familiar puzzle format does not by itself teach a concept. Each activity needs a short learning objective and a result explanation. Word guessing may support vocabulary; matching needs a meaningful relation that the learner can explain. Sean drafts and checks the learning material with Sherwin; Christian checks whether the rule can be implemented as described.

The user confirmed that exact mini-game rules are not yet agreed. No exact score threshold, board size, dictionary, word length, lesson count or attempt limit is approved by the supplied document. Put those values in one short rules sheet before building content around them.

Levels, characters and art​

Retain the approved friendly rounded 3D style: the blue-haired explorer in yellow, screen-faced robots and compact island scenery. See the visual brief. The source reports an existing player controller and models; reuse them before commissioning replacements.

Build a small representative level first. Level count and art quantity follow the measured effort to finish that level. Prior artwork and the old illustrated PDF remain visual/history references; their old mechanics and screen layouts are superseded.

Profiles, results and progress​

A learner code selects a profile stored on that device. It is not an authenticated online account. Switching learners must clear the previous learner's visible progress before showing the next profile.

Only one mini-game receives gameplay input at a time. Loading, saving, pause and board resolution must prevent accidental duplicate actions. Show “saved” only after SQLite confirms the write. A save failure offers a retry and must not erase the last good record.

Christian must settle whether score means latest, best or cumulative score, and whether attempts count guesses, question responses or completed playthroughs. Sean must check that the chosen meaning supports the approved evaluation. See the data reference.

UI and accessibility​

Miguel provides profile, menu, in-game instructions, result, pause and save-error screens. Use readable text and generous touch targets. Essential instructions must work with sound off, and feedback must use text or icons as well as color. Show the current objective and available action clearly.

The player flow defines navigation and recovery. The test checklist defines the evidence needed before beta.

Delivery and ownership​

Sherwin owns learning-game rules and scope; Christian owns implementation and integration; Luis owns art; Sean owns instructional copy and manuscript; Miguel owns UI and supports documentation/testing.

Fixed beta: November 3–6. Fixed pre-final: November 21, 2026. First accepted loop: October 18 planning target. Integrated candidate: October 30 planning target. Testing, manuscript work and rehearsal remain in the task plan.

The old record-ordering activity, three-copy simulation, classifier and grid-agent implementation requirements are withdrawn by the user's October 12 decision. Their archived specifications are not work to add alongside the three new modes.
