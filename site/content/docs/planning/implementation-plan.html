Parallel game implementation plan​

Prepared October 8, 2026. Pre-final defense: November 21, 2026 (44 calendar days away). This is an execution design, not proof of delivered functionality or a guarantee of school completion. Original CH issue dates remain publication history. The revised local October 8 forecast below supersedes the October 5 forecast after the user proposed November 3–6 beta testing at Tambunan National High School, Marinduque. Actual hours are unknown; the user authorized balanced planning estimates. Game implementation and actual device evidence remain unverified; rubric and phone specifications are retained.

Scope and authority​

Use the baseline, PRD, GDD, technical requirements, flow, design brief and database schema. User decisions override documents. Recommendations stay proposed until accepted or validated. Game implementation belongs in Chainy-Game; this repository owns management, specifications and existing board tooling.

All CH-R01–12 remain required. Implement three levels with bounded free placement/configuration, three local replicas, example-trained classification, a short agent challenge, SQLite saves and teacher-mediated export. Reduce art and content quantity before removing required learning concepts. No new gameplay backend is implied by the existing Cloudflare board-sync service.

Scope mentor verdict: validate first, then proceed with bounded mechanics. The strongest evidence is the unverified device/toolchain and capacity, the last zero-progress report, and mandatory pilot/manuscript work. Parallel agents can prepare isolated modules but cannot substitute for on-device integration, site approval, or human review. The next observable gate is a reproducible installed APK plus SQLite/relaunch/export evidence by the existing October 9–11 targets. If this fails, reforecast openly.

Phase 0: repository organization and contract preparation​

Historical proposals, classroom exercises and the stale issue draft are now under docs/archive. Their exact content is retained, including obsolete JSON and status statements. The move manifest records old/new paths and SHA-256 hashes. Active reference paths remain stable to preserve existing skill and board links. Root README/AGENTS, .agents, docs/backlog.json and tools/kanban-sync retain their operational roles. Ignored dist and .wrangler are generated/local state, not source documents to reorganize or delete.

The documentation index is the entry point. Each fact has one authority: baseline for accepted scope, PRD for acceptance, GDD for gameplay rules, technical design/contracts for implementation, SQL for table definitions, GitHub issues for execution status, backlog.json for publication inventory. Do not copy and independently edit the same rules in parallel.

Before implementation dispatch, read the applicable game repository AGENTS.md, inspect its current files and uncommitted changes, pin the base commit, and map proposed paths below to actual paths. The game source was not inspected during this management-document task. Do not treat these paths as already implemented.

Parallel execution model​

One coordinator dispatches bounded packets; a reviewer checks each handoff; Christian controls integration and shared Unity scenes. Human Lead/Support/Reviewer fields remain the existing named assignments, distinct from temporary AI agent roles. This plan combines parallel AI execution with named student-team ownership, consistent with the request to balance each member time commitment.

Use up to three concurrent worker agents plus one coordinator when four agent slots are available. Slots are a concurrency ceiling, not a staffing estimate. Run fewer lanes when review capacity or dependencies require it. Give each agent one packet, one base commit and an exclusive write allowlist. Read access can overlap. A specialist review does not automatically require another agent.

Integration and acceptance workflow​

  1. Coordinator checks the current GitHub issue and dependencies, repository state and accepted contracts. Never infer implementation status from this plan or an open/closed issue alone.
  2. Create an isolated branch/worktree where supported (codex/ prefix); preserve other working changes. Assign an exact file allowlist. If a shared checkout is required, separate paths strictly and reserve shared files to the integrator.
  3. Agent implements only its packet, using synthetic data. Run relevant rule/contract checks and report device checks still pending. Commit Unity metadata with assets. Only the integrator changes Packages, ProjectSettings, bootstrap scenes, shared assemblies or the canonical schema unless explicitly delegated for one packet.
  4. Handoff includes task ID, base/head commit, file list, requirements covered, test output, build/content/schema versions, remaining gaps and a demonstration recipe. Another worker's uncommitted edits must not be included.
  5. Named reviewer examines correctness, educational meaning and regressions. Merge one packet at a time; update consumer fixtures if an approved contract changes. Agent self-tests alone do not establish acceptance.
  6. Integrator builds the combined APK; Miguel executes assigned device cases, Christian reviews technical results. Confirm airplane-mode play, suspend/relaunch, valid saved progress and safe error behavior at each slice.
  7. Update the existing issue with reviewed acceptance evidence when authorized. Keep published IDs and Trello mapping intact; update backlog publication metadata only after confirmed remote writes. This document task did not publish changes or move cards.

No gameplay completion claim follows from generated code, a green editor test or a document heading. Evidence levels are planned, implemented, device-verified and evaluated. Record the actual level for each requirement.

Definition of ready and done​

Ready: prerequisite acceptance is linked; scope/contract versions are named; ownership paths do not collide; synthetic fixtures exist; unresolved decisions are either excluded from this packet or block it explicitly. A draft can explore a blocked question, but cannot be merged as the settled production decision.

Done: the exact requirement's acceptance passes, reviewer records disposition, integrated build is identified where applicable, documentation is consistent, and material limitations are explicit. CH-R01/09/11 require real-device evidence. CH-R12 additionally needs school-required manuscript and pilot evidence. No calculation based on task counts proves 60 percent completion.

Parallel documentation and media delivery before game implementation​

For the requested complete GDD, use three workers plus the coordinator. Worker A owns the GDD draft only; worker B owns media files, captions and provenance manifest; worker C owns an independent validation report and reads all outputs without rewriting authors' files. The coordinator owns baseline/design-brief/schedule reconciliation and integration. In this run, coordinator dispatch may assign a dedicated planning worker first, then reuse its slot for validation. Never exceed the available slots or give simultaneous ownership of one file.

Shared input contract: the user's template and attached references; current baseline/PRD/GDD rules; immutable mechanic IDs; first two attachments as definite visual style, third as gameplay/context only; device specs and rubric unchanged; all four required mechanics retained. Draft text and assets can proceed concurrently after that contract is recorded. Media generation receives the same character/world/UI direction and produces accompanying illustrations, not claimed game screenshots. Preserve original reference media with explicit provenance; generated media must be labelled.

Exit gate: coordinator incorporates actual asset paths and captions, then a validator other than the author checks every requested template section, image role, rule/flow cross-reference, scope boundary, schedule arithmetic and known unknown. Authors correct findings in their own paths; coordinator performs the final link and consistency review. Human acceptance remains with Sherwin, Christian for technical claims, Sean for learning/research wording, Luis for art and Miguel for UI.

Subsequent coding waves use exclusive rules/UI/records/content directories and the contract table above. A completed media/GDD packet permits contract review; it does not bypass CH-03/04 device/store proof, school permissions, or the original finish-to-start dependencies.
