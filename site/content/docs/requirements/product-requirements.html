Chainy product requirements document​

Version 0.1 — October 8, 2026. Product owner: Sherwin Limosnero. This document consolidates the current product contract; it does not claim implemented features, school approval or measured learning gains. Baseline governs confirmed decisions; the GDD specifies gameplay. “Background schema” means the SQLite database schema, as clarified by the user.

Product purpose and audience​

Chainy is a single-player, offline Android educational game for learners aged 13–17 at Cryptita Plays outreach and mini-library sites. Learners explore a top-down 3D setting and build, inspect and revise small systems to understand linked records, validation and tamper detection, agreement among replicas, learning from examples, and agent actions. English is confirmed for the first version. Reading proficiency, prior knowledge and access needs remain to be checked with the site; age alone does not establish them.

The product hypothesis is that visible cause-and-effect activities, explanation and retry can support understanding of these concepts. This is a design rationale to evaluate, not a claim of demonstrated effectiveness. Engagement, completion and usability must be reported separately from learning outcomes.

The project runs September 2026–April 2027. The November 21, 2026 pre-final requires functional core modules, completed manuscript chapters and pilot-area evidence. The stated 60 percent completion requirement lacks a supplied calculation; neither task counts nor levels completed establish compliance. Preserve November integration, QA, pilot work and rehearsal time.

Scope and decision status​

Confirmed: offline Android gameplay; single-player Unity/C# direction and touch controls; three levels within two thematic worlds; free component placement and configuration; multi-node synchronization puzzle; AI-agent delivery challenge; badges and level progress; SQLite as the primary local store; English first; separate game source repository. The teacher-issued learner code proposal is adopted as offline profile identification.

Recommended bounded realization, pending validation: one reusable compact exploration scene with themed areas; up to 12 objects per workbench; three logical replicas on one device; two initial classifier classes; a tiny local nearest-centroid classifier; one short visible-policy agent route. The user accepted an assistant recommendation for AI implementation; the particular prototype still needs a learning and device check. Numerical limits and content quantities are not new confirmed requirements.

Recommended exclusions before pre-final: public blockchain/real cryptocurrency, multiplayer, cloud AI, microphones, automatic cloud sync, a teacher website, content downloader, currency economy and certificates. These recommendations do not cancel any user-required mechanic. Management tools such as GitHub/Trello synchronization are outside the game runtime and are not evidence of game completion.

Latest October 8 decisions: preserve the supplied phone specification and school rubric; use Chainy storyboard Images 1–2 as the definite visual direction and BlockForge Image 3 only for gameplay context. Tambunan National High School, Marinduque is a possible beta site for November 3–6. Individual hours are unknown; the user authorizes balanced estimates in the team plan. These updates do not establish booking, capacity or a tested build.

Unknown: actual school criterion meanings/completion formula, exact tested devices, per-person sustained capacity, pilot booking/custodian, approved instruments and retention, final Unity patch/render path/SQLite binding, and prototype performance. Zero reported implementation remains the latest progress statement. Keep the supplied 32-point rubric intact; do not substitute a different standard or infer a completion percentage.

User journeys​

  1. First learner session: staff issues a code → learner enters study/code → app explains creation of a new local profile → tutorial and mission → explore/build/test/retry → quiz → commit progress → summary. The new-profile warning helps catch valid-format typing mistakes.
  2. Returning learner: select the same local code → continue from last valid checkpoint → complete or replay a mission. Historical attempts remain distinct; replay does not erase first-attempt evidence.
  3. Shared device: pause → confirm switch → end the active session → select the next code. No screen, checkpoint or pending submission may leak the previous learner's state into the next session.
  4. Teacher collection: open staff export → choose approved scope → inspect count → save via device file picker → transfer by the approved method → importer validates → teacher verifies receipt. Saving a file is not proof of receipt and never triggers automatic deletion.
  5. Interruption/recovery: app resumes after process loss → validates database/content → reports an interrupted session → restores the last committed checkpoint or safe mission start. Failed submission is retryable without duplicate evidence.

The detailed screen/state contract belongs in the app flow; technical design defines recovery and persistence behavior.

Quality and evidence constraints​

  • Required gameplay and its learning content must be packaged locally. APK distribution, teacher file transfer and app updates are separate operations, not exceptions silently added to offline gameplay.
  • Proposed performance budgets and candidate device support are in hardware validation. They are targets to test, not measured minimum specifications. Do not make a compatibility promise from editor playback.
  • Use readable English, concise prompts, text/icon feedback alongside color, audio-independent instructions and touch alternatives to precise dragging. Usability and reading difficulty require site/learner checks.
  • Save results, checkpoint and progression consistently; present success only after commit. Do not collect per-frame telemetry, names, unrestricted free text or recordings by default.
  • Keep participant exports, identity maps, credentials and signing keys out of repositories and issues. A teacher-held identity map makes the dataset pseudonymous, not anonymous.
  • Content, app, schema and research instrument versions must remain distinguishable. Do not silently change assessment prompts in a frozen study build.
  • No severe startup, data-loss, core-completion or incorrect-learning-feedback defect may be concealed by a favorable average score.

Evaluation and success criteria​

Technical readiness: each applicable CH-R acceptance check has reproducible evidence and no unresolved core-blocking defect; device/update/export evidence accompanies the build. This is a delivery criterion, not a school completion percentage.

Learning evidence: educator-reviewed, versioned items test ordering/links, integrity/replicas, and examples/agent reasoning. Preserve pre/post pairing rules and first attempts; report missing data and assistance. No target learning gain, sample size, statistical significance or validated instrument is invented here.

Usability evidence: observe whether learners understand prompts, operate controls and explain error feedback; record actual difficulties separately from conceptual scores. The GDD's 30–45-minute gameplay estimate and QA's 45–60-minute total session estimate include different activities and remain untested.

School readiness: obtain the actual criterion descriptions, map each mandatory artifact to evidence, and have the school/adviser clarify the completion calculation. Complete manuscript results from actual data; document unavailable evidence as a blocker.

Parallel delivery and change control​

Use the implementation plan for agent work packets, shared-file ownership, dependency gates and integration sequence. The user requests balanced commitments across team members, not identical task counts. Balance work by discipline, dependencies and verified availability; retain existing accountable issue owners while assigning substantive support execution and review. Product requirements remain stable inputs: gameplay agents consume GDD activity contracts; UI consumes app-flow states; persistence consumes the schema; evidence tooling consumes the export contract. A change to fields, completion semantics or content IDs requires an explicit handoff to every affected lane before parallel implementation continues against it.

Scope-mentor verdict: validate first. The baseline records zero reported implementation and unverified capacity/devices; a document package cannot establish feasibility. Preserve all required mechanics at bounded scale, prove the first Android/SQLite slice, and reduce decorative asset quantity/effect cost before renegotiating required concepts or the confirmed visual identity. Observable next checks are the October 9–11 device/export spike and October 18 level 1 vertical slice. The revised conditional forecast requires an integrated beta candidate by October 30 and readiness checks October 31–November 2 for the possible November 3–6 school sessions. Missed gates require an explicit reforecast; preserve subsequent fixes/analysis, manuscript and November 17–20 rehearsal time before the November 21 defense.

Learning-design verdict: validate first. Each concept now has player action, reasoning and feedback, but learner understanding and assessment quality remain unmeasured. Review the item blueprint with the educator and observe an internal session before a real pilot.

Simulation-accuracy verdict: proceed with explicit simplifications. Retain the existing trusted-reference comparison, one-corrupt-replica assumption, held-out classifier examples and visible agent policy. Acceptance must demonstrate the counterexamples in the GDD; no claim of a production blockchain, generative AI or causal learning improvement follows.
