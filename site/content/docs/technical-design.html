Chainy technical design​

Adopted October 12, 2026 from Christian Jude Villaber's supplied design. The user identifies it as written and verified by the Tech Lead. This reference summarizes that design; open inconsistencies are listed explicitly.

How the game is organized​

LayerPlain-language purposeComponents
PresentationShow the game and capture player actionsUI, input devices, UI Manager
Game logicDecide what an action means and run the current activityInput Manager, Game Manager, Quiz/Wordle/BlockMatch Managers, Level Manager, SceneLoader, Progress Manager
DataSave and retrieve local recordsDatabase Manager, SQLite

The Event Bus carries commands and notifications between components. The Service Locator supplies registered services. UI Manager listens to events and is explicitly excluded from Service Locator registration. Game Manager activates only one mini-game at a time.

This is a simplified responsibility diagram. The source's full diagram also includes Dialogue Manager and object pooling.

Component responsibilities​

ComponentOwnsImportant boundary
Input ManagerConvert raw touch/pointer/keyboard input into game commandsIgnore input that is invalid during load, pause, save or board resolution
Event BusRoute commands and notificationsSubscribers must not remain active after their scene/session ends
Game ManagerApp state, session lifecycle, start/pause/resume/exit, active mini-gameRoute gameplay to one mode only
UI ManagerScreens, HUD and feedback from eventsNo SQL; not registered in Service Locator
Level ManagerLevel content, difficulty, objectives and configurationData comes through Progress Manager in the source architecture
SceneLoaderLoad/unload scenes and report success/failureGame Manager waits for readiness before starting play
Quiz ManagerQuestions, answer evaluation and scoringReturn a result for persistence
Wordle ManagerGuess validation, letter evaluation and outcomeFollow the agreed dictionary and repeated-letter rules
BlockMatch ManagerBoard moves, matches, cascades and objectivesFinish board resolution before accepting another move
Object PoolingReuse objects and effectsReset objects when returned/reused
Progress ManagerProgress, unlocks, checkpoints and read/write coordinationRequest storage operations and report their outcome
Database ManagerParameterized SQL, transactions and schema changesCentral storage access; returns data or an explicit error
SQLiteLocal content and learner recordsNo automatic cloud synchronization
Service LocatorRegister and resolve service dependenciesValidate required services during startup
Dialogue ManagerLearning dialogue/interactions shown in the source diagramExact responsibility/API is absent from Part II; Christian must reconcile it

Do not create replacement manager frameworks to match the old generated design. Work with the actual project structure and the Tech Lead's existing scripts.

Load and save flows​

Load: profile input → Progress Manager → Database Manager → SQLite → Progress Manager → interested systems and UI. Activate the selected learner only after the read succeeds. A missing profile and a database error must lead to different messages.

Save: active mini-game produces a result → Game Manager handles session state → Progress Manager requests a save → Database Manager writes it → Progress Manager reports success/failure → UI shows the outcome.

Recommended reliability rule: save related result/progress changes together; a retry must not count the same completion twice. The exact identifier and transaction are Christian's CH-04 decision. A save failure must leave the last successful save available.

Return or switch learner: finish or resolve the current pending save, stop the active mode and clear its UI/state before loading the next profile. Pause/relaunch: resume a supported saved point; do not promise exact mid-animation or mid-cascade restoration. See the flow reference.

Data and implementation status​

The database reference adopts User, Module, Lesson, User_Progress and User_Analytics as the source model. It preserves uncertain field names and data meanings as questions. No new runnable schema or migration is implied.

Part VI reports SQLite, profile, Quiz, UI and models in progress; player movement completed; Wordle and BlockMatch not started. The evidence named is summarized in the baseline. Source file names are reported evidence, not files inspected in this repository.
